# ADR-0040: subcomando prune-backups — limpeza manual de backups legados

> Status: Superado na v0.1.37 quanto à interface. O `prune-backups` exige pelo menos um entre `--max-age-secs` e `--max-count`, mais um ou mais PATHS de arquivo (senão sai com 2). `--dry-run` é uma flag opt-in, desligada por padrão. A saída é uma linha `pruned` por backup e uma linha `summary` (`action`, `total`). Sem casamento sai com 0 e `total` 0.

- Status: Aceito
- Data: 2026-06-17
- Contexto: A v0.1.21 (ADR-0038) mudou o padrão de `keep_backup` para `false`: os backups são apagados após o sucesso, e os operadores que querem retenção forense passam `--keep-backup`. A migração no local dos backups da v0.1.20 está fora do escopo da v0.1.21, pois a auditoria classificou explicitamente os irmãos `.bak.<timestamp>` anteriores à v0.1.21 como "lixo transitório que o operador pode limpar quando quiser". O fechamento do GAP-2026-014 v2 documentou que `cleanup_old_backups_in` (atomic.rs:833-858) ainda existe para o caso `--keep-backup` (poda por contagem), mas não faz nada pelo caso legado em que o operador usou o anel de backups implícito da v0.1.20. Operadores que atualizam da v0.1.20 para a v0.1.21 herdam um irmão `.bak.<timestamp>` para cada escrita `--backup` que já emitiram. Em hosts de longa duração que atualizaram semanalmente, isso pode chegar a dezenas de milhares de arquivos. A auditoria revelou a necessidade de uma limpeza one-shot que seja: (a) explícita (o operador a roda de propósito, não como efeito colateral de outro subcomando), (b) segura (padrões que não podem causar perda de dados sem uma etapa de confirmação) e (c) componível (usa o mesmo jail de `--workspace` e o mesmo envelope NDJSON do resto da CLI). O invariante `rules-rust-cli-one-shot §Daemon Proibido` proíbe qualquer processo em segundo plano ou agendador, então a limpeza precisa ser uma invocação one-shot que o operador roda num script ou num terminal. A seção "Time Machine" do `docs/AGENTS.pt-BR.md` já documenta a convenção de nomes dos backups (`.bak.<YYYYMMDD_HHMMSS>`) e as regras do jail de `--workspace`, então o novo subcomando herda esses contratos sem inventar novos.

- Decisão: Adicionar um novo subcomando `prune-backups [PATHS]...` na v0.1.22 que apaga os irmãos `.bak.<YYYYMMDD_HHMMSS>` sob os caminhos informados (ou sob a raiz do workspace se nenhum caminho for informado). Três novas flags controlam o conjunto a apagar: `--max-age-secs <SECONDS>` (apaga os backups mais antigos que N segundos, padrão 0 = apaga todos), `--max-count <N>` (mantém no máximo os N backups mais recentes por diretório, padrão 0 = ilimitado) e `--dry-run` (imprime no stdout, como NDJSON, a lista do que seria apagado sem remover nada, padrão `true` por segurança). O subcomando emite uma linha NDJSON por backup inspecionado: `{"path": "...", "age_secs": N, "size_bytes": N, "action": "deleted" | "kept" | "would_delete"}`. Uma linha final `summary` informa `scanned`, `deleted`, `kept`, `elapsed_ms` e `dry_run` (bool). O exit code é 0 se a varredura terminou (independentemente de quantos foram apagados), 1 se nenhum backup foi encontrado (NO_MATCHES) ou 65 se alguma pré-condição falhou (idade inválida, contagem inválida, violação do jail). A implementação vive em `src/commands/prune_backups.rs` e reaproveita o helper `validate_path` da camada de resolução de caminho do G121 (ADR-0031) para impor o jail de `--workspace`. A exclusão usa `std::fs::remove_file` diretamente (não o pipeline atômico), porque o alvo é um backup, não um arquivo primário: o `tempfile + fsync + rename` do pipeline atômico é desnecessário quando o alvo é o irmão descartável.

- Consequências:
  - + Operadores com anéis de backup da era da v0.1.20 têm um comando de uma linha para limpá-los: `atomwrite --workspace . prune-backups --max-age-secs 0` apaga tudo o que for mais antigo que 0 segundo (ou seja, tudo). O padrão `--dry-run` `true` torna o comando seguro para colar de uma conversa sem perder dados.
  - + A flag `--max-count` cobre o caso `--keep-backup` por outro ângulo: um operador que quer "manter os 3 backups mais recentes por diretório" pode rodar `prune-backups --max-count 3` de forma agendada. A flag não exige que `--keep-backup` tenha sido usada, pois opera sobre o estado em disco independentemente de como os backups foram criados.
  - + O subcomando é componível com o resto da CLI: `prune-backups` é uma invocação one-shot, emite NDJSON, respeita o jail de `--workspace` e não exige um processo de longa duração. O NDJSON de saída pode ser consumido pelo `jaq` em scripts (`prune-backups --dry-run | jaq -r 'select(.action == "would_delete") | .path'`).
  - + Os backups apagados pelo `prune-backups` não estão sujeitos ao padrão `keep_backup: false` da v0.1.21 (que afeta apenas a exclusão pós-sucesso do backup recém-criado). O subcomando opera sobre arquivos existentes, não sobre o ciclo de vida do backup de uma nova escrita.
  - - O padrão `--max-age-secs 0` combinado com o padrão `--dry-run` `true` significa que o erro mais comum (o operador esquece que `--dry-run` já está ligado e a segunda invocação apaga tudo) é mitigado pelo padrão. O erro oposto (o operador passa `--dry-run false` e perde dados) é mitigado pelo nome explícito da flag e pelo campo `summary.dry_run` na saída, mas não pode ser impedido pelo próprio subcomando.
  - - O subcomando amplia a superfície do help em uma entrada e adiciona 3 flags. A quantidade de flags é o mínimo necessário para expressar "todos", "mais antigos que N segundos" e "manter no máximo N": a auditoria identificou esses como os três modelos de retenção que os operadores de fato usam.
  - - Os backups apagados pelo `prune-backups` são irrecuperáveis. O VCS pode ter o estado pré-escrita, mas o anel de backups da v0.1.20 foi enquadrado explicitamente como uma rede de segurança forense para o momento pré-escrita sem VCS. Um operador que dependia do backup como única cópia de um arquivo e roda `prune-backups --dry-run false --max-age-secs 0` perderá essa cópia. O campo `summary.dry_run` e a flag explícita `--dry-run` são as únicas guardas.

- Justificativa: A auditoria de 2026-06-15 (ADR-0035) e o release v0.1.21 (ADR-0038) fecharam o problema voltado ao futuro (novas escritas não deixam lixo persistente), mas deixaram o problema voltado ao passado (os backups legados da v0.1.20 persistem) para uma ação explícita do operador. A auditoria rejeitou a alternativa "poda por idade embutida no pipeline atômico" (ADR-0038, alternativa 3) porque ela reintroduz a pergunta "quando eles somem", que a v0.1.21 resolveu ao responder "depois que a escrita que os criou tem sucesso". Para o caso legado, a resposta precisa ser "quando o operador rodar `prune-backups`", porque os backups anteriores à v0.1.21 foram criados por um caminho de código diferente com outra semântica, e nenhuma regra automática de retenção pode ser aplicada retroativamente sem surpreender o operador. O subcomando é a menor superfície que trata o caso legado: um subcomando, três flags, um padrão (`--dry-run true`) que não pode causar perda de dados. O padrão `--dry-run true` é o inverso da convenção do projeto (os padrões costumam ser `false`) e se justifica pela natureza irreversível da operação: o VAI-PSIQUE-CHECK da auditoria (valide-ação-irreversível-pré-psique) está embutido no padrão. O subcomando não interfere no comportamento padrão da v0.1.21: as escritas da v0.1.21 que passam `--keep-backup` criam backups que o `prune-backups` também pode gerenciar, de modo que um único comando de limpeza cobre tanto o modelo de retenção legado quanto o atual.

- Alternativas consideradas:
  1. Poda automática em toda escrita que cria um backup. Rejeitado pelo ADR-0038 (alternativa 3) pelo mesmo motivo: uma idade de 0 segundo é "apagar imediatamente" e uma idade diferente de zero reintroduz a pergunta do "quando". O subcomando é a contrapartida explícita.
  2. **Poda automática no `init` ou na primeira escrita de uma sessão.** Rejeitado: os backups da v0.1.20 são dados do usuário (uma rede de segurança forense que o operador escolheu criar), e apagá-los em silêncio no `init` seria um bug de perda de dados, não uma limpeza. O padrão `--dry-run true` do subcomando e a invocação explícita são o único caminho seguro.
  3. **Embutir a limpeza no `cleanup_old_backups_in` (a poda por contagem de atomic.rs:833-858).** Rejeitado: o `cleanup_old_backups_in` opera sobre o anel de backups de uma única escrita em andamento, não sobre o estado global dos arquivos `.bak.*` em disco. Misturar os dois forçaria um refactor da camada atômica e acoplaria o ciclo de vida da v0.1.21 ao problema de limpeza legada. O subcomando mantém as duas preocupações separadas.
  4. **Distribuir um binário one-shot separado (`atomwrite-prune-backups`).** Rejeitado: viola o invariante `rules-rust-cli-one-shot` (um binário, vários subcomandos) e obriga os operadores a gerenciar uma segunda instalação. O subcomando é o mesmo binário, o mesmo envelope NDJSON, as mesmas regras de jail.

- Gatilho para revisitar: Se os operadores relatarem que o padrão `--dry-run true` é incômodo (querem encadear `prune-backups --dry-run false` num script), adicionar uma flag `--force` que exija uma etapa de confirmação (prompt de TTY ou `--yes` para pular) e trocar o padrão para `--dry-run false` nessa combinação de flags. Se o VAI-PSIQUE-CHECK se mostrar insuficiente e os operadores relatarem perda acidental de dados, adicionar uma flag `--backup-of-backup` que cria uma cópia `.bak.<timestamp>.prune-safety` de cada backup antes da exclusão, ao custo de dobrar o uso de disco durante a limpeza. Se um subcomando futuro (por exemplo `prune-journals`, `prune-sidecars`) precisar da mesma limpeza por padrão, extrair a saída NDJSON e a semântica das flags `--max-age-secs`/`--max-count` para um helper compartilhado em vez de copiar e colar o padrão.

- Adendo (implementação da v0.1.22): Durante a execução descobrimos duas correções que o ADR original não antecipou:

  1. **Semântica de `--max-count N`**: A especificação original dizia "manter no máximo os N mais recentes". A implementação inicial tinha `truncate(max_count)` depois de inverter a ordenação, o que apagava os N backups mais recentes em vez dos N mais antigos. A correção é `truncate(backups.len().saturating_sub(max_count))` na ordenação ascendente (apagar o prefixo mais antigo). O teste de regressão `prune_backups_max_count_keeps_newest_n` fixa o comportamento corrigido.

  2. Endurecimento do VAI-PSIQUE-CHECK: Quando nem `--max-age-secs` nem `--max-count` são informados, o clap resolve `Option<u8>::None` para `None` (sem filtro), e o loop de poda apagaria em silêncio todos os backups que casam com o alvo. A implementação agora recusa com `bail!()` ("refusing to prune without --max-age-secs or --max-count; pass at least one to define the retention policy"). O teste de regressão `prune_backups_no_filter_aborts_with_error` fixa essa verificação de segurança.

  Ambas as correções estão documentadas nos próprios nomes dos testes, e futuros leitores do código podem rastrear a intenção até este adendo.
