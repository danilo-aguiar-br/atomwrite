# ADR-0036: `--partial` no `edit` — par único continua NO_MATCHES, multi-par aplica os que casaram

- Status: Aceito
- Data: 2026-06-15
- Contexto: O G117 (ADR-0026) introduziu a cascata fuzzy de 9 estratégias para o `edit` multi-par e o relatório por par `PairResult { matched, strategy, similarity }`, mas não definiu o comportamento do `--partial` no caso de par único. A flag foi adicionada ao `EditArgs` como placeholder, documentada na `SKILL.md` como "opt-in — aplica os pares que casam e relata o resto", e a auditoria da v0.1.19 (GAP-2026-005b) confirmou que o help nunca renderizou a flag, porque a declaração clap do campo foi entregue sem implementação. O fechamento do GAP-2026-005b na v0.1.20 é a implementação do próprio `--partial`, e essa implementação levanta uma questão semântica: quando um `edit --old X --new Y --partial` de par único não encontra `X` no arquivo, o que o comando deve fazer? Três respostas são coerentes: (a) ter sucesso silenciosamente com zero pares aplicados e exit 0 (a leitura "permissiva"), (b) devolver `NO_MATCHES` (exit 1) para espelhar o comportamento do `replace`, (c) devolver `INVALID_INPUT` (exit 65) para espelhar o caminho de erro tudo-ou-nada do multi-par. O caso multi-par é inequívoco: `--partial` aplica os pares que casaram, relata os que não casaram em `pair_results` e sai com exit 0 com `edits < pairs_total`. Mas uma chamada de par único sem nenhum casamento não tem nada a aplicar, e "aplicou 0 de 1" é um caso degenerado que, dependendo do parser do chamador, pode parecer idêntico a uma edição bem-sucedida sem efeito. Sem uma semântica clara, gates locais a jusante que buscam `edits: 0` com grep deixariam passar silenciosamente um pipeline que deveria ter falhado.

- Decisão: Adotar a assimetria de forma explícita: **`--partial` de par único sem casamento devolve `NO_MATCHES` (exit 1), e `--partial` multi-par aplica os pares que casaram e relata os que não casaram em `pair_results` (exit 0 com `edits < pairs_total`)**. Concretamente:
  1. **Par único (`args.old.len() == 1`)**: em `edit_old_new_single`, em `src/commands/edit.rs:438-462`, quando `match_pair` devolve `Err(_)`, o ramo `Err(_) if args.partial` mapeia para `AtomwriteError::NoMatches` (exit 1, nenhuma escrita realizada). Justificativa: a mesma invocação de par único sem `--partial` teria devolvido `INVALID_INPUT` (exit 65), e a flag `--partial` não relaxa a semântica de falha do caso degenerado de par único, porque o chamador não pediu de fato "aplique o subconjunto que casa" (o subconjunto é o conjunto vazio). Espelhar o `NO_MATCHES` mantém a semântica do `replace --no-matches` e dá aos gates locais um único exit code para buscar com grep ("se exit 1, o arquivo ficou inalterado porque nada casou").
  2. **Multi-par (`args.old.len() > 1`)**: em `edit_old_new_multi`, em `src/commands/edit.rs:650-705`, o loop por par acumula `pair_results`, e num erro de `match_pair` com `args.partial` definido, o loop registra um `PairResult { matched: false, ... }` e CONTINUA para o próximo par em vez de abortar. A escrita acontece se, e somente se, pelo menos um par casou. O exit é 0, e o envelope `EditOutput` carrega `pairs_total`, `edits` (o número realmente aplicado) e o array completo `pair_results`, para que o chamador possa auditar quais pares foram pulados.
  3. **Padrão tudo-ou-nada (sem `--partial`)**: quando a flag está ausente, QUALQUER par sem casamento no caminho multi-par aborta o lote inteiro com `AtomwriteError::EditPairFailed { failed_pair_index, total, pair_results }` (ADR-0026, exit 65). O caminho de par único sem `--partial` também aborta com `INVALID_INPUT` (exit 65). O padrão é estritamente mais conservador que o `--partial`, então pipelines existentes que não optaram por ele não são afetados.
  4. Caso de borda multi-par com zero aplicados: quando `--partial` está definida e nenhum par casa, o caminho multi-par devolve `NO_MATCHES` (exit 1, sem escrita). Isso espelha o caso de par único para manter o exit code de resultado vazio consistente entre as quantidades de pares.
  5. Disciplina de schema: o campo `mode` do `edit-output.schema.json` vira `fuzzy-multi(N)` quando algum par casou por fuzzy e `exact-multi(N)` caso contrário (o ADR-0026 já fixa isso para o caminho multi sem partial). A flag `--partial` não é refletida separadamente no schema, mas `pairs_total` e `edits` juntos permitem a um consumidor detectar o caso parcial calculando `edits < pairs_total`.

- Consequências:
  - + A semântica é explícita e documentada: o `--partial` de par único é, na prática, um no-op com aviso (exit 1), porque há apenas um par a aplicar, e o `--partial` multi-par é uma aplicação parcial de verdade. Quem lê a seção da SKILL responde "o que o --partial faz?" contando os pares.
  - + Gates locais podem confiar no `NO_MATCHES` (exit 1) como o sinal universal de "nenhum casamento encontrado" em `edit` e `replace`, independentemente do `--partial` ou da quantidade de pares. O comportamento é consistente.
  - + O padrão tudo-ou-nada é preservado: agentes que encadeiam o `edit` em um pipeline sem `--partial` recebem a mesma garantia de atomicidade de antes. O opt-in `--partial` é uma válvula de escape estritamente aditiva.
  - + O `--partial` multi-par devolve um array estruturado `pair_results`, então um chamador que quer saber quais pares específicos falharam pode auditar sem reexecutar a edição. O valor de diagnóstico do G117 é preservado.
  - - O comportamento do `--partial` de par único é contraintuitivo à primeira vista: um usuário que passa `--partial` a um comando de par único e recebe exit 1 pode abrir um bug. Mitigado pela seção da SKILL que afirma explicitamente "`--partial` de par único sem casamento sai com 1, `--partial` multi-par aplica o que casou".
  - - A tabela de exit codes cresce uma linha (exit 1 para o caso partial de par único, além do exit 1 já existente para o caso multi-par com zero aplicados). Ambos compartilham o código `NO_MATCHES`, então o schema não muda, mas a documentação narrativa precisa ser precisa.
  - - Um chamador que quisesse detectar especificamente "par único, sem casamento, --partial definida" (em oposição a "qualquer caso sem casamento") teria de olhar o campo `mode` em vez do exit code. O campo mode é um discriminador de string que os pipelines existentes já interpretam, então isso é uma dependência aditiva, não uma quebra.

- Justificativa: O caso de par único não pode ser parcial por definição: há exatamente um par, então o subconjunto que casa é o conjunto inteiro (casou) ou o conjunto vazio (sem casamento). A flag `--partial` nesse caso degenerado não tem efeito observável na *escrita*, apenas no *código de erro*: ela rebaixa `INVALID_INPUT` (exit 65, "o arquivo está quebrado e sua edição foi rejeitada estruturalmente") para `NO_MATCHES` (exit 1, "o arquivo está bem, mas sua string antiga não estava presente"). O rebaixamento é útil: um editor automatizado que tenta de novo em divergências transitórias quer exit 1, não exit 65, para distinguir "tente de novo com outro --old" de "aborte o lote". O caso multi-par, por contraste, tem uma semântica parcial real: "aplique 7 de 10 pares, relate os 3 que não casaram". A assimetria, portanto, é fundamentada, não arbitrária. O ADR-0026 já estabeleceu que o `--partial` é desligado por padrão (tudo-ou-nada) para preservar a atomicidade, e o comportamento de par único da v0.1.20 é uma consequência natural desse mesmo princípio tudo-ou-nada aplicado no nível da unidade de falha (um par).

- Exemplos:
  - `atomwrite edit foo.rs --old "ALPHA" --new "beta"`: sem casamento (ALPHA ausente), `--partial` não definida → `INVALID_INPUT` (exit 65), sem escrita, envelope de erro no stdout.
  - `atomwrite edit foo.rs --old "ALPHA" --new "beta" --partial`: sem casamento, `--partial` definida → `NO_MATCHES` (exit 1), sem escrita, envelope de erro no stdout. O chamador vê exit 1 e pode tentar de novo com outro `--old` ou tratar a ausência como esperada.
  - `atomwrite edit foo.rs --old "A" --new "X" --old "B" --new "Y"`: `A` casa, `B` não, `--partial` não definida → `INVALID_INPUT` (exit 65), sem escrita, o envelope inclui `failed_pair_index: 2, total: 2, pair_results: [...]`.
  - `atomwrite edit foo.rs --old "A" --new "X" --old "B" --new "Y" --partial`: `A` casa, `B` não, `--partial` definida → exit 0, escrita realizada (apenas a substituição A→X), envelope `pairs_total: 2, edits: 1, pair_results: [{matched: true, ...}, {matched: false, ...}]`.
  - `atomwrite edit foo.rs --old "A" --new "X" --old "B" --new "Y" --partial`: NENHUM casa, `--partial` definida → `NO_MATCHES` (exit 1), sem escrita. Espelha o caso de par único no nível multi-par: zero pares aplicados mapeia para o mesmo exit code de um par sem casamento.

- Alternativas consideradas:
  1. Fazer o `--partial` de par único sair com exit 0 e `edits: 0`. Rejeitado: uma saída bem-sucedida com zero pares aplicados é uma armadilha. Gates locais que buscam exit 0 deixariam passar silenciosamente um pipeline que deveria ter sinalizado a string antiga ausente. O `NO_MATCHES` (exit 1) é o sinal conservador e encontrável com grep.
  2. Fazer o `--partial` de par único sair com exit 0 e aplicar a string `new` no fim do arquivo. Rejeitado: um append não solicitado não é um "edit", é um `write --append`, e confundir os dois viola o princípio de que os verbos devem corresponder à semântica. O verbo `edit` implica "achar X, trocar por Y", e se X está ausente, a operação é um no-op ou uma falha, nunca um append.
  3. Unificar o comportamento de par único e multi-par sob uma regra só: `--partial` sempre aplica o subconjunto que casa, exit 0 se pelo menos um par foi aplicado, exit 1 se nenhum. Rejeitado: o caso de par único não tem "subconjunto", tem 1 ou 0 aplicações. Tratar "aplicou 1 par" de forma idêntica a "aplicou 7 de 10 pares" obscurece a diferença estrutural. A assimetria é o modelo mais limpo.
  4. Adicionar um novo exit code (por exemplo exit 67 `EDIT_PARTIAL_EMPTY`) para o caso partial de par único. Rejeitado: 26 exit codes já são um fardo de manutenção, e a tabela de exit codes da SKILL da v0.1.20 cresceria uma linha por um caso degenerado. O código `NO_MATCHES` é o sinal canônico existente para "a operação não achou nada a fazer", e o caso partial de par único é exatamente isso.

- Gatilho para revisitar: Se um chamador futuro pedir que "o `--partial` de par único ainda grave o arquivo mesmo quando nada casou" (por exemplo, uma ferramenta de templates que trata `--old` como dica e `--new` como append incondicional), revisitar a semântica. Se o caso multi-par com zero aplicados virar um problema de usabilidade (o chamador não consegue saber se `--partial` foi definida ou se a entrada estava vazia), adicionar um discriminador `pairs_applied: 0` ao envelope de erro. Se um release v0.2.0 introduzir um novo namespace de exit codes, reavaliar o reuso do `NO_MATCHES` para o caso partial de par único.
