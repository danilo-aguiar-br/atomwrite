# ADR-0037: `GlobalArgs.lang` → `--locale` — liberando o namespace `--lang`

> Histórico (pré-0.1.35): os knobs de produto `ATOMWRITE_*` / env descritos abaixo foram superados. A configuração de runtime é apenas flags de CLI + `config.toml` XDG / `atomwrite set|get`.


- Status: Aceito
- Data: 2026-06-15
- Contexto: A auditoria da v0.1.19 achou o GAP-2026-003: `atomwrite scope --lang rust` é rejeitado com `ARGUMENT_PARSE_ERROR` (exit 2), embora o help do subcomando `scope` liste `--lang` como alias de `--language`. A causa raiz é uma colisão de namespace. O `GlobalArgs.lang` (`src/cli.rs:114-130` na v0.1.20, `#[arg(long = "lang", global = true, env = "ATOMWRITE_LANG", ...)] pub lang: Option<String>`) reivindica a flag longa `--lang` no nível superior. A macro derive do clap promove as flags globais à frente das flags do subcomando, então, quando o usuário passa `--lang rust` numa invocação de `scope`, o parser a associa ao `GlobalArgs.lang` (com o valor `"rust"`) e depois reclama que `ScopeArgs.language` (que é `required = true` na struct em `src/commands/scope.rs:24-44`) está ausente. Adicionar `alias = "lang"` ao `ScopeArgs.language` não ajudaria: o mecanismo de alias não consegue disparar quando uma flag global com o mesmo nome longo já associa a entrada. Um relatório direto de colisão do clap é suprimido em algumas versões do clap, e no build da v0.1.18 o resultado foi uma mensagem confusa de "required argument missing". Existem três correções candidatas: (A) manter o `--lang` global e aceitar que `scope --lang` está quebrado para sempre, (B) renomear a forma longa da flag global para `--locale` preservando a variável de ambiente (`ATOMWRITE_LANG`) e o nome do campo Rust (`lang`), (C) fazer o `ScopeArgs.language` usar o estilo builder `Arg::new`, com associação explícita apenas curta a `-l` e uma forma longa que não colida. A opção A é a linha de base recomendada pela auditoria para a v0.1.20 (o help foi ajustado para explicar a limitação), mas o problema de UX de fundo permanece e o namespace `--lang` fica permanentemente fora do alcance de quem escreve subcomandos. A opção C é a mais invasiva (toca o contrato derive do clap em todo subcomando que usa dicas de linguagem: `scope`, `query`, `outline`, `transform`). A opção B é a menor mudança, a mais local, com o maior retorno.

- Decisão: Adotar a opção B na v0.1.20. Especificamente:
  1. Renomear a flag longa da CLI de `--lang` para `--locale` via `#[arg(long = "locale", ...)]` no campo `GlobalArgs.lang`. O nome do campo Rust continua `pub lang: Option<String>` para preservar a API programática (`args.global.lang` não muda). A variável de ambiente continua `ATOMWRITE_LANG` para preservar os consumidores de variáveis de ambiente (executores de scripts, wrappers de contêiner, exports de shell). Referência de código: `src/cli.rs:114-130` agora tem `long = "locale"` com o atributo `env = "ATOMWRITE_LANG"` existente.
  2. **Liberar o namespace `--lang`** para uso no nível dos subcomandos. O `ScopeArgs.language` em `src/commands/scope.rs:24-44` agora declara `#[arg(short = 'l', long = "language", alias = "lang", required = true, help = "Language (rust, py, ts, go, c, etc); accepts --lang as alias")]`. O GAP-2026-003 da auditoria está fechado: `atomwrite scope --lang rust` agora é válido.
  3. Mudança incompatível na superfície da CLI: toda invocação que antes passava `--lang <locale>` como flag de nível superior DEVE migrar para `--locale <locale>`. Não há alias de transição, porque aliases no nível global reocupariam o namespace, e a quebra limpa é o único caminho para um `--lang` permanentemente livre.
  4. A variável de ambiente e o nome do campo NÃO são incompatíveis: usuários programáticos (`cli::GlobalArgs { lang: Some("pt-BR".into()), .. }`) e wrappers de shell que exportam `ATOMWRITE_LANG=pt-BR` não veem mudança. A única superfície que quebra é a flag longa `--lang` digitada por humanos no nível global.
  5. O guia de migração é publicado no CHANGELOG da v0.1.20 e nos dois arquivos SKILL (EN e PT): uma receita de uma linha com `sed` troca `--lang <X>` por `--locale <X>` nos scripts, e os executores de scripts que definem a variável de ambiente não são afetados.
  6. A docstring do campo renomeado documenta a renomeação, a preservação da variável de ambiente, a motivação do namespace e a natureza deliberadamente incompatível. Referência de código: `src/cli.rs:114-130` carrega uma docstring de 10 linhas com a referência ao `ADR-0037`.

- Consequências:
  - + `atomwrite scope --lang rust` agora é interpretado de forma idêntica a `atomwrite scope --language rust` e a `atomwrite scope -l rust`. Três grafias da mesma intenção, sem colisão de namespace e sem achado de auditoria para rediscutir.
  - + Subcomandos futuros (`query`, `outline`, `transform`) que precisem de uma forma curta `--lang` podem usar o mesmo padrão `alias = "lang"` sem mais mudanças no `GlobalArgs`. O namespace está livre para sempre.
  - + A variável de ambiente `ATOMWRITE_LANG` continua funcionando: qualquer contêiner ou wrapper de shell que exporte o locale continua se comportando como antes. O nome de campo `pub lang: Option<String>` mantém a API programática estável: `args.global.lang` devolve o mesmo valor, o mesmo tipo, a mesma semântica.
  - + A mudança incompatível é delimitada: um único token superficial, encontrável com grep (`--lang` → `--locale`). Operadores que rodam `rg '\\-\\-lang\\b' .` nos seus scripts e receitas acham todas as ocorrências de uma só vez.
  - - Operadores que automatizaram a antiga flag `--lang` verão um erro duro de `unknown argument`. A migração é mecânica (trocar `--lang` por `--locale`), mas É uma mudança incompatível, e as notas de release precisam destacá-la explicitamente. É um custo deliberado, pois a alternativa (um `scope --lang` quebrado para sempre) é pior.
  - - A forma longa `--locale` é um pouco mais longa que `--lang`, e em pipelines de shell longos os caracteres extras somam. A troca é aceita: a alternativa (o namespace `--lang` permanentemente fechado para subcomandos) obriga cada autor de subcomando futuro a inventar uma flag curta diferente, o que fragmenta a API.
  - - A renomeação para `--locale` é a segunda renomeação da CLI visível ao usuário neste ciclo (a primeira foi a renomeação apenas de documentação de `SYNTAX_ERROR` para `SYNTAX_ERROR_DETECTED` no ADR-0033). Operadores que leem o CHANGELOG verão duas entradas de renomeação, a justificativa de cada ADR é independente, mas a rotatividade cumulativa nos aliases de shell é um custo real.

- Guia de migração:
  - Scripts de shell (uma linha): `rg -l '\\-\\-lang\\b' bin/ scripts/ && sd -- '\\-\\-lang\\b' '--locale' bin/ scripts/`. Revise o diff e faça o commit. A receita troca apenas o token `--lang` isolado, e a variável de ambiente `ATOMWRITE_LANG` não é tocada.
  - Consumidores de variável de ambiente: nenhuma mudança necessária. `ATOMWRITE_LANG=pt-BR` continua definindo o locale, e a renomeação ocorre apenas na superfície da flag longa da CLI.
  - Usuários programáticos (API Rust): nenhuma mudança necessária. `args.global.lang` não muda.
  - Consumidores da documentação (receitas da SKILL): atualizar de `--lang <X>` para `--locale <X>` nos exemplos voltados ao usuário. O nome de campo interno `pub lang: Option<String>` e a variável de ambiente `ATOMWRITE_LANG` não são voltados ao usuário na SKILL.
  - Aliases e wrappers (funções de shell, `alias atomwrite-lang='atomwrite --locale'`): crie aliases novos e NÃO crie alias para a forma antiga `--lang`, porque a forma antiga agora dá erro duro.

- Justificativa: A tensão fundamental está entre (a) preservar a compatibilidade retroativa de uma flag que já estava quebrada no espírito (a colisão do `scope --lang`) e (b) abrir o namespace para a longa lista de subcomandos futuros que precisam de uma forma curta `--lang`. Preservar o `--lang` global na v0.1.20 significa que o GAP-2026-003 continua aberto e que todo subcomando futuro ciente de linguagem (candidatos da v0.1.21+: `lint --lang`, `format --lang`, `ast-print --lang`) teria de escolher outra flag curta ou disparar a mesma colisão. A renomeação limpa na v0.1.20 paga o custo da quebra uma vez e libera o namespace para sempre. A preservação da variável de ambiente e do nome do campo (as duas superfícies de que dependem os consumidores programáticos e de ferramentas) faz da mudança incompatível uma mudança apenas no nível do *shell*, e o custo é pago por humanos digitando a flag, não pela camada de ferramentas. A ausência deliberada de um alias de transição `--lang` é o que torna o namespace realmente livre, e um alias de transição apenas reocuparia o namespace e adiaria o mesmo problema para a v0.2.0. A entrada do CHANGELOG, o guia de migração da SKILL e a receita com `sd` deste ADR, juntos, tornam a migração mecânica e encontrável com grep.

- Alternativas consideradas:
  1. Manter `GlobalArgs.lang` como `--lang` e documentar a limitação (linha de base da v0.1.20 recomendada pela auditoria). Rejeitado: o GAP-2026-003 continua aberto, o help do `scope` precisa carregar uma ressalva permanente, e todo subcomando futuro ciente de linguagem fica impedido de usar a forma curta natural.
  2. Adicionar `alias = "lang"` ao `ScopeArgs.language` e tentar contornar a colisão global com o builder do clap (estilo `Arg::new`). Rejeitado: o contorno em estilo builder é local a um subcomando, não se generaliza para `query` / `outline` / `transform` e introduz inconsistência (alguns subcomandos têm `--lang`, outros não). A renomeação é um único ponto de mudança que resolve o problema globalmente.
  3. Mover a variável de ambiente para um novo nome (por exemplo `ATOMWRITE_LOCALE`) e renomear o campo para `pub locale: Option<String>` para ter simetria total com a flag da CLI. Rejeitado: dobra a superfície da mudança incompatível. A variável de ambiente é a mais estável das duas (matrizes de teste locais e wrappers de contêiner dependem dos nomes de variáveis de ambiente, enquanto as flags longas da CLI são digitadas por humanos que podem ler uma entrada de CHANGELOG). Manter a variável de ambiente e o nome do campo estáveis, renomeando apenas a flag longa, é o caminho de menor ruptura.
  4. Fornecer um `#[arg(alias = "lang")]` de transição no próprio `GlobalArgs.lang` (além do novo `long = "locale"`). Rejeitado: um alias de transição reivindica o namespace de novo e perpetua a mesma colisão. A quebra limpa é o único caminho para um `--lang` permanentemente livre.
  5. Promover a renomeação a um salto de versão maior (v0.2.0). Rejeitado: a renomeação é uma mudança única, mecânica e substituível com grep. Subir a versão maior por uma renomeação `--lang` → `--locale` sinaliza uma mudança de API muito maior do que o diff real justifica, e a linha v0.1.x já carrega o mandato de auditoria de "fechamento de gaps pós-release". A mudança incompatível está documentada no CHANGELOG da v0.1.20 e no guia de migração.

- Gatilho para revisitar: Se um subcomando futuro revelar uma terceira forma curta em conflito que exija outra renomeação de flag global, considerar promover a próxima renomeação a um salto de versão maior. Se operadores relatarem que a receita de migração deixou escapar uma classe de wrapper (por exemplo, aliases de shell em arquivos rc obscuros), adicionar uma variante de receita com `sd` ao guia de migração. Se uma ferramenta a jusante consome o binário `atomwrite` e interpreta o `--help` para descobrir flags, a nova flag `--locale` é o nome canônico, e a ferramenta precisa ser atualizada junto com o binário.
